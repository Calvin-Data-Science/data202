// ── Section 1: What a Row Means, After Melting ───────────────────────────────

::W04-R2-Q1 Row meaning after melting::
In Monday's class, plot_yields starts with one row meaning "one plot's whole season." After pd.melt() unstacks the six Week*_lbs columns into a Week / Harvest_lbs pair, what does one row of the resulting long table mean?{
=One plot, in one week #Correct. Melting turns column names into values of a new column, so each new row narrows down to a single plot-week combination instead of a whole season.
~Still one plot's whole season, just with fewer columns #Melting changes what a row means — it doesn't just trim columns while leaving the row's meaning the same.
~One week, across every plot #That describes a groupby summary built from the long table, not what a single melted row means.
~One plot, one crop #That's what exploding the Crops column produces, not what melting the week columns produces.
}

// ── Section 2: melt() Mechanics ───────────────────────────────────────────────

::W04-R2-Q2 id_vars vs. value_vars::
In pd.melt(yields, id_vars=['Plot_ID', 'Gardener', 'Crops'], value_vars=['Week1_lbs', ..., 'Week6_lbs'], var_name='Week', value_name='Harvest_lbs'), what role do id_vars play?{
=They are the columns that get repeated, unchanged, on every new row — they still identify which plot a row belongs to #Correct. id_vars stay fixed; they're what keeps each new row anchored to a specific plot.
~They are the columns being unstacked into the new Week / Harvest_lbs pair #That's value_vars's job — id_vars are left alone, not unstacked.
~They become the values inside the new Week column #id_vars stay as their own columns; it's value_vars' names that become Week's values.
~They are dropped from the output entirely #id_vars are kept on every row, not dropped — melting only unstacks value_vars.
}

// ── Section 3: pivot_table() Mechanics ────────────────────────────────────────

::W04-R2-Q3 What columns= does in pivot_table::
long.pivot_table(index=['Plot_ID', 'Gardener', 'Crops'], columns='Week', values='Harvest_lbs') reverses Monday's melt, giving back an (18, 9) table. What does the columns= argument specify?{
=Which column's distinct values (e.g. "Week1", "Week2", ...) should become new column headers in the wide result #Correct. Each distinct Week value turns into its own column, exactly reversing what melt() did.
~Which columns should be dropped before pivoting #Nothing is dropped here — pivot_table() rearranges every value it's given.
~Which columns identify a row, staying fixed #That's what index= specifies, not columns=.
~Which column supplies the numbers that fill in the new cells #That's what values= specifies, not columns=.
}

// ── Section 4: Exploding and What value_counts() Then Means ─────────────────

::W04-R2-Q4 Reading value_counts() after exploding::
After splitting Crops on commas and exploding it, one row of the result means "one plot, growing one crop." What does exploded['Crop_List'].value_counts() showing lettuce at 7 actually tell you?{
=Lettuce is grown in 7 of the 18 plots #Correct. Since each row after exploding is one plot-crop pair, value_counts() is counting plots per crop, not pounds.
~7 total pounds of lettuce were harvested across the season #Exploding multiplies rows, not harvest weight — no pounds are summed by value_counts() here.
~Lettuce was harvested in 7 out of the 6 tracked weeks #Weeks aren't part of this table at all; Crops was never linked to the Week column.
~7 different varieties of lettuce are grown in the garden #value_counts() counts rows matching the exact string "lettuce," not different varieties of it.
}

// ── Section 5: Why Some Questions Need the Long Format ───────────────────────

::W04-R2-Q5 A question the wide table couldn't answer::
Only after melting could long.groupby('Week')['Harvest_lbs'].sum() reveal that the garden's harvest peaks in Week 3 (194.8 lbs) and tapers by Week 6 (67.5 lbs). Why couldn't this be answered directly from the original wide plot_yields table?{
=The wide table has no single column that says "which week" — that information was split across six separate column names, so there was nothing to group by #Correct. groupby() needs a column to group on, and "week" only became a column once the table was melted.
~The wide table didn't actually contain the Week 3 harvest numbers #The wide table has every one of those numbers — the problem is they're spread across separate columns, not missing.
~groupby() only works on long tables, never wide ones #groupby() works on any table; the real issue is whether a usable "which week" column exists to group by.
~Melting added new harvest data that the wide table was missing #Melting only rearranges existing data — it adds no new information, just a new shape.
}

// ── Section 6: Review — Named Aggregation (Week 3) ───────────────────────────

::W04-R2-Q6 Review: named aggregation vs. dict-of-lists::
From Week 3: .agg(avg_support=('monthly_support_usd', 'mean')) is named aggregation. What's its main advantage over the dict-of-lists style, e.g. .agg(\{'monthly_support_usd': ['mean']\})?{
=It lets you assign custom, readable output column names directly, instead of ending up with a stacked column structure per statistic #Correct. Named aggregation produces one flat, clearly-named column per result, which is often easier to read than the dict style's output.
~It is the only way to compute more than one statistic per group #Both styles can compute multiple statistics per group — dict-of-lists just does it with a list of function names per column.
~It runs faster because it skips Python function calls entirely #Both styles ultimately call the same underlying aggregation functions — the difference is in output shape and naming, not speed.
~It works only with numeric columns, while dict style works with any column type #Named aggregation works with any column and any valid aggregation function, same as the dict style.
}
