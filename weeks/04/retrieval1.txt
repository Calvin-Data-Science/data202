// ── Section 3: When Charts Deceive ───────────────────────────────────────────

::W04-R1-Q3 Classifying a deceptive chart, with real numbers::
top5_nations shows England with 369 total goals and Brazil with 97 — a big gap already. Suppose someone charts this with a y-axis that starts at 300 instead of 0, making England's bar look enormous and every other country's bar nearly invisible by comparison. Which of the three ways charts can mislead does this represent?{
=Misrepresentation — a truncated axis distorts the proportions between bars, exaggerating the visual gap beyond what the actual numbers show #Correct. Bar charts encode value through bar length starting at zero; cutting that off breaks the encoding and is the textbook example of misrepresentation.
~False impression — the data is accurate, so a visual choice merely suggests a pattern that isn't there #Close, but the course specifically files a truncated axis under misrepresentation (distorted proportions), not the false-impression category.
~Ambiguity — the chart doesn't specify what's being measured #Ambiguity is about missing labels, units, or context; this chart can carry full labels and still mislead through distorted proportions.
~None of the three — starting a y-axis above zero is always fine for a bar chart #Bar charts specifically rely on bar length from zero to represent value; truncating the axis is exactly the kind of choice that misleads.
}

A bigger total can reflect a bigger group, not a higher rate — exactly the sums-favor-big-groups distortion from Monday's class.
~Yes — a bigger total always means a higher rate per player #This is the exact misconception the notebook warns about; here the smaller group actually has the higher per-player rate.

// ── Section 5: Custom Aggregation with lambda, Reviewed ──────────────────────

::W04-R1-Q5 Why age_range_by_team needed a lambda::
Task 03B.3 asked for the range of Age per team (oldest minus youngest) using .agg(lambda x: x.max() - x.min()) instead of a built-in aggregation name like 'mean' or 'sum'. Why was a lambda needed here instead of just passing a string?{
=pandas doesn't ship a built-in "range" statistic, so a custom function has to compute it directly from each group's values #Correct. .agg() accepts any function, including a lambda, for exactly this situation — a statistic no built-in name covers.
~Lambdas are required any time you group by more than one column, and Team is the only column here, so this is actually unnecessary #This isn't about how many columns you group by; a lambda is needed because "range" isn't a built-in statistic, regardless of grouping structure.
~.agg() cannot accept built-in function names at all, only lambdas #This contradicts every named-aggregation and list-of-functions example used all week, like .agg(['mean', 'sum']).
~A lambda is needed because Age is a categorical column, not numeric #Age is a numeric column; max() and min() (and their difference) are ordinary numeric operations.
}

// ── Section 6: Lookup vs. Regex, Reviewed ─────────────────────────────────────

::W04-R1-Q6 Why a dictionary, not a pattern, for nation names::
Task 03A.3 used an explicit nation_map dictionary with .replace() to turn "ESP" into "Spain" — codes not in the dictionary, like "NOR", were simply left as their 3-letter code. Why couldn't a regex pattern have derived "Spain" from "ESP" the way regex cleaned other messy text this week?{
=Regex can only rearrange or match text that's already in the string; it has no way to invent the word "Spain" from the three letters "ESP" without being told that mapping #Correct. This is the same abbreviation problem as "SF" -> "San Francisco" from Monday's class — regex works on patterns of existing characters, not on outside knowledge.
~Regex only works on lowercase text, and "ESP" is uppercase #Case isn't the issue here — regex handles uppercase text fine, and the problem is deriving new information, not matching case.
~"ESP" contains a digit, which regex cannot process #There's no digit in "ESP" at all; this isn't why a lookup was needed.
~.replace() with a dictionary is actually a form of regex, so this is a regex solution too #Dictionary-based .replace() is a literal lookup of exact values, not a pattern-matching operation — that's precisely why it can do what regex can't here.
}
